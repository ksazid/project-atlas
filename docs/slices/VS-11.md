# VS-11 — Notifications

## Goal
Provide a business-isolated, owner-controlled notification experience for meaningful Atlas events without introducing third-party delivery dependencies or changing the PES framework.

## Scope

- in-app notification preferences per Business
- deterministic notification records derived from authoritative Atlas activity
- Today Focus availability reminders
- Outcome follow-up reminders when a recorded follow-up becomes due
- Weekly Review availability reminders
- read/unread state
- stable deduplication keys
- deep-link targets back into existing Atlas screens
- audit records for preference changes and notification state changes
- mobile notification center and preference controls within existing PES navigation conventions

## Boundaries

- no Expo push provider activation
- no APNS/FCM credentials
- no SMS, WhatsApp or email provider activation
- no paid third-party service
- no background production scheduler
- no production deployment or enablement
- no PES routing/auth/state-management restructuring
- notification records do not imply an Action was completed or an Outcome was caused by Atlas

## Data model

### NotificationPreference
One row per Business. Stores enabled categories and concurrency version.

### NotificationRecord
Append-oriented user-facing notification record containing BusinessId, category, stable deduplication key, title/body, optional deep-link target, created timestamp and read timestamp.

## Generation policy
Generation is deterministic and idempotent. The API may materialize missing notification records from authoritative data when the owner loads the notification center. Stable keys prevent duplicates.

Eligible foundations:

- current Today Focus Opportunity
- Outcome follow-up timestamp at or before now
- Weekly Review period availability

Generation respects the Business notification preferences before creating records.

## Security and isolation

- every endpoint requires BusinessOwner authorization
- ownership is resolved from the authenticated provider subject
- all queries are scoped by BusinessId before record access
- cross-Business IDs return not found
- writes are audited

## Acceptance criteria

- preferences can be read and updated safely
- disabled categories never materialize new notifications
- repeated refreshes do not duplicate records
- unread count is deterministic
- individual notifications can be marked read
- all notifications can be marked read for the current Business
- deep-link targets use existing Atlas routes only
- mobile supports loading, empty, error and refresh states
- mobile preference controls are accessible and do not alter PES structure
- CI, Security baseline and Product intake pass before certification
