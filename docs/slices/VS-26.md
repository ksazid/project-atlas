# VS-26 — Google Place Intelligence & Goal-First Onboarding

## Outcome

Reduce repetitive onboarding by enriching a uniquely resolved Business through one bounded Google Places API (New) Place Details request, showing only high-value operating details for explicit owner confirmation, moving Goals ahead of optional non-goal context, and suppressing questions already satisfied by owner-submitted canonical context.

## Scope

1. Keep the existing Google Text Search location resolution as the Business identity boundary.
2. After one exact Place ID is selected/preselected, allow at most one bounded Place Details enrichment request in the current owner interaction.
3. Use an explicit centrally tested field mask; never use `*` and never fetch reviews, review summaries, ratings, photos or broad attributes merely because they exist.
4. Keep Google Places response content transient. Retain the Place ID only as provider content. Atlas must not persist a Google Places payload or hidden Google-derived facts.
5. Present a compact `About your business` confirmation using the approved Atlas design. If an owner explicitly chooses/confirms a canonical operating answer, persist that answer as owner-submitted Business Context rather than as copied Google content.
6. Move onboarding from Business confirmation to Goals before optional progressive context.
7. Suppress progressive questions whose target context is already satisfied by owner-confirmed canonical context. Target 0–3 optional non-goal questions for sufficiently enriched Businesses; five remains the degraded/missing-context ceiling.
8. Preserve safe degraded behaviour when Places is unavailable, unconfigured, rate-limited or missing fields.

## Google policy boundary

Execution-time review on 2026-08-11 confirmed:

- Place Details (New) requires a field mask.
- Place IDs are exempt from Places caching restrictions and may be stored/reused.
- Other Places API content is subject to storage/caching restrictions and attribution requirements.
- EEA-linked projects have additional permitted-use constraints.

Therefore VS-26 uses Google-rich attributes only as interaction-transient suggestions. Persistence occurs only for a separate explicit owner-submitted canonical answer. No Google response JSON, attribution payload, or unconfirmed rich attribute is stored as Business Context.

## Non-goals

- Google Maps HTML scraping
- reviews/review text/review summaries
- ratings or review counts
- Google Business Profile private APIs
- private Bolt/Wolt/POS/reservation connectors
- goal inference from public/provider data
- duplicated VS-25 media/menu ingestion
- navigation redesign
- production release/deployment/enablement

## Design

Preserve `ATLAS-DESIGN-001` v1.2: warm-neutral/deep-green Atlas visual grammar, shared tokens, existing `BrandMark`, low cognitive load, concise cards/forms, accessible errors, ~44×44 targets, dynamic type, reduced motion and no third-party visual imitation. Provider attribution appears only where required for transient provider content.

## Security / reliability

- server-side API key only;
- exact Place ID input from trusted location resolution;
- bounded timeout/response/JSON depth;
- no wildcard field mask;
- no API key or provider payload in logs/errors;
- owner/business authorization on enrichment endpoints;
- missing provider fields mean unknown, not false;
- provider failure never blocks otherwise valid Business creation.

## Acceptance

- exact Place ID and explicit field-mask tests pass;
- Google rich content is not persisted;
- explicit owner-submitted canonical operating context is persisted with owner authority;
- confirmed channel context suppresses the redundant restaurant service-channel question;

- enriched flow presents no filler questions and targets at most three optional non-goal questions;
- degraded flow retains the maximum-five safety ceiling;
- authentic create-business, Goals and progressive-question mobile regressions pass;
- API/mobile CI, Security baseline and Product Intake pass on exact certification head;
- no release or production enablement without separate exact-SHA approval.
