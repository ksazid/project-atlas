# VS-08 — Outcome Capture and Business Memory

## Requirements

Implements approved PRD requirements **FR-11 — Outcome capture** and **FR-14 — Business Memory**.

## Scope

- Capture an Outcome for an eligible Business Opportunity/Action after owner-controlled execution.
- Support usefulness, owner-reported result, time spent, optional notes, measurable results and follow-up date.
- Classify Outcome evidence as `measured`, `owner-reported`, `estimated` or `unknown`.
- Preserve exact Business, Opportunity, Goal, Action and Knowledge Pack provenance.
- Use optimistic concurrency and business-isolated authorization.
- Maintain transparent structured Business Memory derived only from product-relevant data.
- Expose Business Memory as inspectable records rather than opaque hidden model state.
- Permit deletion of outcome-derived memory without mutating historical Opportunity/Action records.
- Extend the existing Opportunity/Execution Kit flow without restructuring PES.

## Outcome model

An Outcome belongs to one Business and one Opportunity. The first MVP implementation supports one current Outcome record per Opportunity with append-oriented revision/audit history planned through immutable audit records. The owner remains the source of truth for owner-reported fields.

Fields include:

- usefulness rating (1–5)
- result summary
- time spent in minutes
- optional owner notes
- optional measurable result name/value/unit
- evidence classification
- optional follow-up date
- captured by / captured at
- exact Knowledge Pack key/version
- optimistic concurrency version

`measured` must include a measurable result. `owner-reported` may contain a qualitative result without a measurable value. `estimated` must be clearly labelled and must never be presented as measured. `unknown` is valid when the owner cannot determine the result yet.

## Business Memory

Business Memory is a transparent product-domain projection, not a hidden AI memory store. MVP memory categories are:

- profile
- goals
- active-knowledge-pack
- action-decision
- rejection-reason
- outcome
- preference / owner feedback where already supported

Each memory item carries a stable key, category, source type, source identifier where applicable, value, captured/updated timestamps and whether the item is deletable.

Outcome capture updates only outcome-derived memory. It does not rewrite historical Opportunities, Actions or Knowledge Pack provenance.

## API

Business-isolated endpoints will support:

- get Outcome for an Opportunity
- create/update Outcome with optimistic concurrency
- list Business Memory
- delete deletable memory items

Every accepted mutation creates an audit record.

## Mobile

Extend existing feature modules only. The owner can capture or update an Outcome from the completed Action flow and inspect the resulting Business Memory summary. PES navigation, routing, authentication, state management, design system and API client architecture remain unchanged.

## Explicitly out of scope

- History browser (VS-09)
- Weekly Review (VS-10)
- notifications/follow-up delivery (VS-11)
- autonomous learning that changes business policy without owner-visible evidence
- vector embeddings or external memory stores
- causal attribution or guaranteed ROI claims
- deployment or production enablement

## Acceptance criteria

1. Outcome capture supports every FR-11 field and evidence classification.
2. Measured outcomes require measurable evidence; estimated/owner-reported/unknown remain visibly distinct.
3. Outcomes are business-isolated and stale writes are rejected.
4. Exact Opportunity, Goal and Knowledge Pack provenance is retained.
5. Business Memory is structured, transparent and product-relevant.
6. Outcome-derived memory can be deleted without deleting historical Action/Opportunity records.
7. Every accepted mutation is auditable.
8. Existing VS-01 through VS-07 behaviour remains backward compatible.
9. PES framework structure remains unchanged.
10. Migration, API policy tests, mobile checks, CI, security baseline and product intake pass before certification.
11. Runtime remains development/test only; no deployment occurs in this slice.
