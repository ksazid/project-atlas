# VS-15 — Context Visual Migration

## Outcome

Migrate the existing authenticated Business Context experience to the approved Atlas warm-neutral/deep-green visual system while preserving the existing Context API, authentication, Business isolation, persistence semantics, and navigation model.

## Requirement

- FR-05 — Business Context

## Scope

- Keep `apps/mobile/app/(tabs)/context.tsx` as the existing route.
- Keep `getContext`, `saveContext`, `loadSession`, and `BusinessContextEntry` unchanged.
- Preserve the existing editable keys: `customers`, `busyPeriods`, `constraints`, and `currentPriorities`.
- Keep every Context field optional and keep Atlas useful with limited data.
- Preserve API-returned provenance and owner-confirmation metadata.
- Require explicit owner confirmation before public Context is eligible for Save, matching the existing API rule.
- Preserve unknown API-returned Context entries through local merge/save behavior.
- Add honest loading, missing-Business, recoverable error, retry, validation, saving, save-error, and success states.
- Preserve owner drafts across recoverable retry/save failures.
- Use shared Atlas design tokens and `BrandMark` only.
- Support logical screen-reader order, accessible busy/disabled/checkbox state, keyboard-safe scrolling, at least 44-point Pressable targets, narrow phones, and contained tablet layouts.

## Acceptance criteria

1. The authenticated owner can load Context only through the existing Business-isolated API boundary.
2. Empty Context is a valid ready state and no field becomes newly required.
3. Existing API values are displayed without changing their stored key, source, or confirmation metadata.
4. Editing a value does not silently rewrite provenance.
5. Public unconfirmed Context is clearly labelled and cannot be submitted until the owner confirms it.
6. Save uses the unchanged `saveContext` boundary and reports success only after server confirmation.
7. Retry and Save cannot overlap; repeated operations are disabled while work is active.
8. Unsaved edits survive recoverable reload and save failures.
9. Unknown non-empty API entries are not discarded by the client when known fields are edited and saved.
10. The screen uses the approved Atlas warm-neutral/deep-green visual system and has no direct temporary-logo references.
11. Mobile tests cover merge, provenance, owner confirmation, optional values, draft preservation, operation serialization, and accessible state presentation.
12. PES validation, mobile validation, preflight, CI, Security baseline, and Product Intake are required on the exact implementation head before certification.
13. Runtime visual evidence is recorded only from an authentic runnable Expo channel; unavailable evidence is reported honestly.
14. No API, domain, migration, authentication, navigation, dependency, deployment, release, EAS, OTA, or production change is introduced.

## Visual composition

- Warm-neutral canvas with content contained to 680 points.
- Header with `BrandMark`, `BUSINESS CONTEXT` eyebrow, benefit-led heading, and concise optional-data guidance.
- Data-minimisation/privacy guidance card.
- One restrained white card per existing Context field with prompt, helper text, multiline input, and provenance treatment.
- Textual `OWNER PROVIDED` / `PUBLIC SOURCE` provenance labels; colour is never the only signal.
- Accessible checkbox confirmation for public values.
- Polite feedback region and one full-width green `Save context` action.

## Risk and security

Risk level: medium.

This is a bounded frontend/customer-flow migration over the already implemented VS-02 Context API. Business isolation, authentication, audit behavior, provenance policy, and server validation remain unchanged. Context guidance continues to minimise data collection and explicitly warns against end-customer personal data.

## Non-goals

- Context API redesign or bulk-replace semantics
- Deleting persisted Context entries
- New Context keys or industry-specific fields
- Connected-source ingestion
- Public-data discovery changes
- AI generation or recommendation changes
- Navigation restructuring
- Global state/query architecture changes
- New dependencies
- Deployment, release, EAS build, OTA update, or production enablement

## Certification evidence

Expected evidence includes Context model tests, full mobile validation, PES planning/governance/slice checks, dashboard/platform validation, preflight, exact-head CI/Security/Product Intake results, independent diff review, and authentic runtime visual/accessibility evidence when the execution environment can produce it.
