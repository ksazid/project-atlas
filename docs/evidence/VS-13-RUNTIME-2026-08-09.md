## Interaction assertions

The capture run and subsequent Task 4 runtime review established the following real rendered behavior:

- 8/8 persisted Profile text inputs/areas rendered.
- Public-unconfirmed Profile blocked Save until the owner confirmation was selected.
- Confirmation enabled Save without changing the API payload shape.
- Opening hours was focused and edited at 390×844; Save remained in the viewport after scrolling.
- The successful PUT returned and persisted the edited Profile; `Profile saved.` was awaited through its polite live region.
- A controlled save 503 displayed the stable draft-safe message, did not render the fixture's private provider error, preserved the edited hours, and re-enabled Save.
- A controlled load 503 rendered the recoverable error state; its 44px Retry action restored the ready form.
- Runtime measurement placed the 390×844 Save action at 52px high and found the 768×1024 document width equal to the viewport width.
- Requests used `Bearer runtime-token` and the seeded `dev-business` boundary only.
- No React/Expo error overlay or page crash was observed. Expected controlled 503 and blocked-image network errors were present in browser console output.

The loading state was transient while the local fixture resolved and was not preserved as a separate screenshot. The missing-session state was reviewed in implementation but was not captured here.

## BrandMark network limitation

`BrandMark` created a correctly sized accessible node labelled `Atlas brand mark`, but this sandbox could not fetch `upload.wikimedia.org`. The original captures recorded `net::ERR_EMPTY_RESPONSE`; the bounded Task 4 rerun explicitly aborted that external host to avoid requesting additional network authority. The mark therefore appears blank in these images.

This proves an environmental trigger for these captures, not a local React layout failure. The implementation also has a pre-production robustness risk because the temporary mark has no local/failure fallback. An approved local Atlas asset/fallback is required before production enablement; this evidence does not invent one or bundle the third-party trademark.

## Native and accessibility limitations

Expo Web verified narrow layout, DOM focus, scrolling, form labels, web checked state, disabled state, 44-point actions, and polite live-region feedback. It cannot instantiate UIKit, display an iOS software keyboard, deliver native keyboard-frame notifications, or observe native scroll insets.

This Linux workspace has no Xcode, iOS Simulator, connected physical iOS device, or native automation channel. The following remain required before release and are not claimed by this record:

- authentic iOS `automaticallyAdjustKeyboardInsets` behavior with Opening hours focused and the software keyboard visible;
- Save reachability and successful save without dismissing the iOS keyboard first;
- native dynamic-type clipping/focus-order review at enlarged system text sizes;
- physical-device interaction validation.
