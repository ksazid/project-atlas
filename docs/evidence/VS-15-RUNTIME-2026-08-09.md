## Runtime boundary

The runtime verifier is `tests/mobile/context-runtime.test.mjs` and executes only when both `CI=true` and `GITHUB_ACTIONS=true`.

The test uses external development fixtures at application boundaries only:

- a local HTTP fixture implements the unchanged `GET` and `PUT /api/v1/businesses/dev-business/context` contract;
- a temporary `apps/mobile/src/auth/session.web.ts` shim supplies the existing session API through browser local storage only for the exported CI runtime and is deleted during test cleanup;
- the browser is seeded with `atlas.access-token=runtime-token` and `atlas.business-id=dev-business`;
- the temporary prototype BrandMark host is blocked so runtime evidence does not depend on external trademark/image availability;
- no tracked API, DTO, auth, database, navigation, dependency, workflow, production configuration, deployment, or release behavior is replaced by the fixture.

The fixture deliberately includes server-normalized known Context keys and an additional unknown Context entry so the real rendered route proves that VS-15 handles both without changing persistence semantics.

## Runtime assertions

The passing run verified all of the following against the rendered Expo Web application:

- initial loading state;
- recoverable load failure and Retry;
- successful retry into the ready Context experience;
- server-normalized `busyperiods` and `currentpriorities` values render in their existing editable fields;
- an additional API-returned Context entry remains visible rather than being silently discarded;
- publicly sourced non-empty Context cannot cross the PUT boundary until owner-confirmed;
- both known and additional public Context expose owner confirmation controls;
- a controlled save failure preserves the edited draft and exposes stable Atlas error copy;
- delayed successful save exposes visible `Saving…`, web `aria-busy=true`, and disabled native/web accessibility state;
- successful server confirmation renders `Context saved.` and preserves the returned draft value;
- every exercised Context request uses `Bearer runtime-token` and the seeded `dev-business` Business boundary;
- the 390×844 and 768×1024 rendered layouts have no horizontal overflow;
- every enabled button and checkbox measured by the runtime is at least 44 CSS pixels high.

The runtime generated 9 authenticated Context requests and 5 successful fixture PUT operations across the failure/recovery/save scenarios.
